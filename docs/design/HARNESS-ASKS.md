# Two asks of Claude Code (2026-10-11)

Status: a letter, not a plan. Quotes are from https://code.claude.com/docs/en/hooks and
/docs/en/sub-agents as served on 2026-10-11. Each ask is one field. Delete this file when both
land or are declined. Context: `docs/INTERFACE-V2.md` "The shape" and the manual's hooks section.

Rechecked 2026-10-18 for 0.18 K1: the [official hooks reference](https://code.claude.com/docs/en/hooks#precompact)
still documents PreCompact veto control, not `compactSummary` replacement. PostCompact's
`compact_summary` observes the generated summary and cannot change it. No pre-compact summary
writer can be implemented against this documented contract yet.

## What the contract says today

PreCompact input (quoted): "In addition to the common input fields, PreCompact hooks receive
`trigger` and `custom_instructions`. For `manual`, `custom_instructions` contains what the user
passes into `/compact` and is `null` when they pass nothing. For `auto`, `custom_instructions` is
`null`." Output: "Exit with code 2 to block compaction. ... You can also block by returning JSON
with `"decision": "block"`." And: "Claude Code discards a PreCompact hook's `systemMessage` and
`continue` fields." Blocking has a sharp edge: "If compaction was triggered to recover from a
context-limit error already returned by the API, the underlying error surfaces and the current
request fails."

PostCompact input (quoted): "PostCompact hooks receive `trigger` and `compact_summary`. The
`compact_summary` field contains the conversation summary generated by the compact operation."
Output: "PostCompact hooks have no decision control. They can't affect the compaction result but
can perform follow-up tasks."

Common fields include `agent_id` ("Unique identifier for the subagent or in-process teammate the
hook fires in") and `agent_type` ("Present when the session uses `--agent` or the hook fires inside
a subagent"). The subagent note names only "tool events such as `PreToolUse` and `PostToolUse`"
as firing inside subagents. The sub-agents page says "Subagents support automatic compaction using
the same logic as the main conversation ... `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` applies to subagents
as well", and its frontmatter table has no compaction field.

So a hook can see a compaction coming and veto it, and can read the summary after the fact. It
cannot write the summary, and it cannot tell one agent's compaction from another's.

## Ask 1: let PreCompact supply the compacted segment

Use case. The public complaint that prompted this: a compaction fires, the summary drops the one
detail the next hour depended on, and there is no undo. cv already answers the undo half with
what exists (`SessionStart` matcher `compact` injects "`cv show <id> --pre-compaction` reads what
was lost; `cv rewind <id> --at N` resumes from before it"; the discarded records stay in the
jsonl). What no hook can do is make the summary *right* in the first place, in place, without a
restart. PreCompact today is a veto only, and the veto is unsafe in recovery mode.

Proposed field. A `hookSpecificOutput` on PreCompact, exit 0:

    { "hookSpecificOutput": { "hookEventName": "PreCompact",
        "compactSummary": "<text the harness uses verbatim as the summary>",
        "keepFromUuid": "<optional: keep records from this uuid on, verbatim>" } }

When `compactSummary` is present the harness skips its own summarizing call and records the hook's
text in the `compact_boundary` record (so PostCompact's `compact_summary` is this text).
`keepFromUuid` is the same shape as the resume gate's own tail-keeping, exposed.

What cv would do. `cv hook pre-compact` reads `transcript_path`, computes the segment the
boundary will cover, and emits what `cv distill` already renders for a span: decisions, files
touched, commit shas, open questions, task ids, with every identifier verbatim and a one-line
pointer to `cv show --pre-compaction`. The summary a lane wakes up with is then the same text the
root reads in `cv lanes`, and `cv show --kind compaction_boundary` shows one seam, authored, not two guesses.

## Ask 2: per-agent compaction: identity on PreCompact, a threshold in frontmatter

Use case. A swarm root wants different policies per role: a scout should never compact (fail loud
and hand off through its own continuation file), a long implementer should compact early and
often, the root itself should compact late. Today there is one session-wide knob
(`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, which "applies to subagents as well"), the frontmatter has
`maxTurns` but nothing about context, and the docs do not say whether PreCompact fires inside a
subagent at all, nor which transcript `transcript_path` names when it does.

Proposed fields. (a) Document PreCompact and PostCompact as firing inside subagents, carrying
`agent_id`, `agent_type` and `agent_transcript_path` exactly as SubagentStop does, with
`transcript_path` still the main session's. (b) One frontmatter field on the agent `.md`:

    compaction: { autoCompactPct: 70 }    # or  compaction: { auto: false }

scoped like `maxTurns`, overriding the session value for that agent type only.

What cv would do. `cv hooks install claude` writes one PreCompact entry whose hook matches on
`agent_type`: it blocks for roles whose policy is "never" (and says so in `reason`, naming the
continuation file to write), passes for the rest, and appends `(agent_id, agent_type, preTokens)`
to the lane ledger so `cv lanes` shows which lanes compacted and `cv doctor` prints the policy in
force per role instead of one number for the whole box.
